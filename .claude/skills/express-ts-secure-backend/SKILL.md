# Express + TypeScript secure backend

Use this for Express 5, TypeScript, Drizzle, PostgreSQL, Redis and BullMQ backends that handle money. Explain in plain language why each rule exists before showing code. Prefer the simplest pattern that works. Make targeted changes only: do not redesign existing structure unless asked. When asked for code, return complete copy-paste-ready files, not diffs. Use native `fetch` (never axios or SDKs) and direct email/password auth (never Passport).

## 1. Folder structure (feature-based)

```
src/
  server.ts              # starts HTTP only
  worker.ts              # starts BullMQ workers only (separate process)
  app.ts                 # builds the Express app, mounts middleware + routes
  config/                # env.ts, db.ts, redis.ts, queue.ts, logger.ts
  common/
    errors/              # app-error.ts
    middleware/          # authenticate, authorize, validate, rate-limit, idempotency, error-handler, request-id
    utils/               # async-handler, money, crypto, pagination, http (fetch with timeout), response, sanitize
    types/               # express.d.ts (Request.user augmentation)
  db/
    schema/              # one file per table, singular names: user.schema.ts
    migrations/          # generated by drizzle-kit and committed
  features/
    auth/ users/ wallets/ deposits/ withdrawals/ ledger/ transactions/ sweeps/ audit/
      <feature>.routes.ts
      <feature>.controller.ts   # HTTP only: read req, call service, send response
      <feature>.service.ts      # business rules
      <feature>.repository.ts   # DB queries only, no business rules
      <feature>.validation.ts   # Zod schemas
      <feature>.types.ts
      <feature>.test.ts
  providers/             # external systems: tron/, mevonpay/, quidax/, coingecko/
  jobs/                  # queue definitions + processors (withdrawal.queue.ts, withdrawal.processor.ts)
```

Rules:
- One naming style everywhere: singular feature name, `kebab-case` folders, `feature.layer.ts` files. No typos in file names.
- Dependencies point one way: routes -> controller -> service -> repository. Features talk to each other only through the other feature's service. Providers never import from features.
- Controllers never touch the DB. Repositories never call audit, queues or other features.
- Delete dead code instead of commenting it out. Remove unused packages.
- Commit `db/migrations`. Never use `drizzle-kit push` against production.
- Never commit `coverage/`, `dist/`, `logs/` or `.env`. Always provide `.env.example`.

## 2. Mitigation checklist (apply to every review/build)

Critical (money and takeover):
1. **No self-credit loops.** A deposit scanner must ignore transfers from the platform's own hot wallet and sweep/gas-top-up addresses. Decide explicitly whether native gas tokens (e.g. TRX) are supported as deposits.
2. **Never pass `req.body` to a DB update.** Parse with a Zod schema that lists only the allowed fields (`.strict()`), then update. Role, verified flag, email, PIN and password change only through dedicated, verified flows.
3. **Every route is private by default.** Mount `authenticate` once on the parent router, whitelist public routes explicitly, and use `authorize('admin')` for admin data. Never return `password`, `pin`, or token hashes: use `sanitizeUser`.
4. **Verify on-chain success, not just inclusion.** Treat a transfer as confirmed only when the receipt result is SUCCESS and the required confirmation depth is met. Reverted transactions must not be marked confirmed.
5. **Withdrawals must be exactly-once.**
   - Require an `Idempotency-Key` header, stored with a unique constraint per user.
   - Write the debit and the queue intent in the same DB transaction (outbox table), and let a relay enqueue it. Never `await` audit logging between commit and enqueue.
   - Persist `broadcasting` state (with a deterministic reference) before sending. If the outcome is unknown (timeout), never refund automatically: reconcile by checking the chain, then decide.
   - Use the withdrawal id as the BullMQ `jobId`.
   - Do not use `pending_${Date.now()}` as a hash. Use nullable `txHash` with a partial unique index.
6. **Protect the PIN.** Count failures in Redis per user (e.g. 5 tries then 15 min lock), return a generic error, and rate-limit the withdrawal route. Require the PIN to be exactly the configured digits.
7. **Signup must prove ownership.** Create the user as `isVerified: false`. Verify the OTP and issue a short-lived, single-use signup token bound to that user; later onboarding steps require that token, not a body `userId`. Login rejects unverified users.
8. **OTPs:** generate with `crypto.randomInt`, store a hash, limit attempts (5) and resends (1 per 60 s), delete on success. Never log secrets, API keys or tokens.

High:
- **Money is never a JS number.** Parse user input to a decimal string, convert to `bigint` minor units with `common/utils/money.ts`, and keep DB columns `numeric`. Convert to a number only for display.
- **Deposit scanning** keeps a cursor (last timestamp or block per wallet+token), pages until it reaches it, dedupes on `(txHash, logIndex or toAddress+token)`, and runs on a schedule job, not from a user button. A manual refresh must be rate-limited.
- **Sweeps** are idempotent: deterministic job id per wallet+token, one sweep at a time per wallet (Redis lock), save status `pending` before broadcast and `confirmed` only after verified success, and check hot wallet gas first.
- **Keys:** never keep the mnemonic or hot-wallet key in plain env in the API process. Use a KMS/HSM or a separate signer service; run workers as a separate process with minimum access.
- **Wallet index allocation** uses a DB sequence or advisory lock, never `max(index)+1`.
- **Refresh tokens:** store only a SHA-256 hash, one row per device, rotate atomically in a transaction, and detect reuse (reuse revokes the family). Mount `cookie-parser` if cookies are used, or use body tokens only.
- **Validate every input** with the `validate` middleware (body, query, params). No route reads raw input.
- **Errors:** throw `AppError` subclasses only; the error handler maps them. One response shape for the whole API.
- **External calls** always use `fetchWithTimeout` with a timeout, bounded retries with backoff for safe (idempotent) calls only.
- Add `helmet`, a restrictive CORS allow-list, a JSON body size limit, `trust proxy` when behind a proxy, global + per-route rate limits, a `/health` endpoint, and graceful shutdown (HTTP, workers, Redis, DB).

Database:
- Foreign keys on every reference; consistent id types (prefer uuid).
- `CHECK (amount > 0)`, enums for `status`/`type`/`entry_type`, `updated_at` maintained, indexes on foreign keys and on `(user_id, created_at)`.
- Ledger rows carry `asset` and `network` directly; keep a per-user-per-asset balance row updated in the same transaction, locked with `SELECT ... FOR UPDATE`. Ledger entries are append-only.

## 3. Utility files to create

### config/env.ts (validate once, fail fast, single source)
```ts
import 'dotenv/config';
import { z } from 'zod';

const schema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().default(5000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  ACCESS_TOKEN_SECRET: z.string().min(32),
  REFRESH_TOKEN_SECRET: z.string().min(32),
  SALT_ROUNDS: z.coerce.number().int().min(10).max(14).default(12),
  CORS_ORIGINS: z.string().default(''),
});

const parsed = schema.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid environment:', parsed.error.flatten().fieldErrors);
  process.exit(1);
}
export const env = parsed.data;
```
Why: one typed object instead of `process.env` scattered everywhere; the app refuses to start with a bad config. Add provider keys (TRON, Resend, etc.) to the schema as features need them.

### common/middleware/validate.ts
```ts
import type { RequestHandler } from 'express';
import type { ZodType } from 'zod';
import { BadRequestError } from '../errors/app-error';

type Schemas = { body?: ZodType; query?: ZodType; params?: ZodType };

export const validate = (schemas: Schemas): RequestHandler => (req, _res, next) => {
  for (const key of ['body', 'query', 'params'] as const) {
    const schema = schemas[key];
    if (!schema) continue;
    const result = schema.safeParse(req[key]);
    if (!result.success) {
      return next(new BadRequestError(result.error.issues.map(i => `${i.path.join('.')}: ${i.message}`).join('; '), 'VALIDATION_ERROR'));
    }
    // Express 5: req.query is a getter, so store parsed data separately
    (req as any).valid = { ...(req as any).valid, [key]: result.data };
  }
  next();
};
```
Controllers then read `req.valid.body` (declare the type in `common/types/express.d.ts`). Use `.strict()` on schemas so unknown fields are rejected.

```ts
import type { RequestHandler } from 'express';
import { ForbiddenError, UnauthorizedError } from '../errors/app-error';

export const authorize = (...roles: Array<'customer' | 'staff' | 'admin'>): RequestHandler =>
  (req, _res, next) => {
    if (!req.user) return next(new UnauthorizedError());
    if (!roles.includes(req.user.role)) return next(new ForbiddenError());
    next();
  };
```

### common/middleware/error-handler.ts
```ts
import type { ErrorRequestHandler } from 'express';
import { AppError } from '../errors/app-error';
import { logger } from '../../config/logger';

export const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
  const isApp = err instanceof AppError;
  const status = isApp ? err.statusCode : 500;
  (status >= 500 ? logger.error : logger.warn)({ msg: err.message, stack: err.stack, requestId: req.id, path: req.path });
  res.status(status).json({
    status: 'error',
    code: isApp ? err.code : 'INTERNAL_ERROR',
    message: status >= 500 ? 'Internal server error' : err.message,
    requestId: req.id,
  });
};
```

### common/utils/money.ts (no floats, ever)
```ts
import { BadRequestError } from '../errors/app-error';

const DECIMAL = /^\d+(\.\d+)?$/;

/** '12.5' + 6 decimals -> 12500000n. Rejects extra precision instead of rounding. */
export const toMinorUnits = (value: string, decimals: number): bigint => {
  if (!DECIMAL.test(value)) throw new BadRequestError('Invalid amount');
  const [whole = '0', frac = ''] = value.split('.');
  if (frac.length > decimals) throw new BadRequestError(`Max ${decimals} decimal places`);
  return BigInt(whole) * 10n ** BigInt(decimals) + BigInt(frac.padEnd(decimals, '0') || '0');
};

export const fromMinorUnits = (value: bigint, decimals: number): string => {
  const base = 10n ** BigInt(decimals);
  const whole = value / base;
  const frac = (value % base).toString().padStart(decimals, '0').replace(/0+$/, '');
  return frac ? `${whole}.${frac}` : whole.toString();
};

export const addAmounts = (a: string, b: string, d = 6) => fromMinorUnits(toMinorUnits(a, d) + toMinorUnits(b, d), d);
export const subAmounts = (a: string, b: string, d = 6) => {
  const r = toMinorUnits(a, d) - toMinorUnits(b, d);
  if (r < 0n) throw new BadRequestError('Insufficient balance');
  return fromMinorUnits(r, d);
};
export const compareAmounts = (a: string, b: string, d = 6) => {
  const x = toMinorUnits(a, d), y = toMinorUnits(b, d);
  return x === y ? 0 : x > y ? 1 : -1;
};
```
Why: `Math.floor(0.29 * 1e6)` gives 289999. BigInt minor units are exact. Fees are computed in minor units too.

### common/utils/crypto.ts
```ts
import { createHash, randomInt, randomBytes, timingSafeEqual } from 'node:crypto';

export const generateOtp = (digits = 6): string => randomInt(0, 10 ** digits).toString().padStart(digits, '0');
export const sha256 = (value: string): string => createHash('sha256').update(value).digest('hex');
export const randomToken = (bytes = 32): string => randomBytes(bytes).toString('base64url');
export const safeEqual = (a: string, b: string): boolean => {
  const x = Buffer.from(a), y = Buffer.from(b);
  return x.length === y.length && timingSafeEqual(x, y);
};
```
Use `sha256` for refresh tokens and OTPs stored in DB/Redis; use bcrypt for passwords and PINs.

### common/utils/http.ts (native fetch with timeout and bounded retry)
```ts
import { AppError } from '../errors/app-error';

export const fetchWithTimeout = async (
  url: string,
  init: RequestInit = {},
  { timeoutMs = 8000, retries = 0 }: { timeoutMs?: number; retries?: number } = {}
): Promise<Response> => {
  let lastError: unknown;
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fetch(url, { ...init, signal: AbortSignal.timeout(timeoutMs) });
    } catch (error) {
      lastError = error;
      if (attempt < retries) await new Promise(r => setTimeout(r, 250 * 2 ** attempt));
    }
  }
  throw new AppError('Upstream service unavailable', 503, 'UPSTREAM_UNAVAILABLE', { cause: lastError });
};
```
Only set `retries > 0` for reads or calls that carry an idempotency reference. Never auto-retry a money-moving broadcast.

### common/utils/response.ts
Keep one shape: `{ status: 'success', message, data?, meta? }` for success and `{ status: 'error', code, message, requestId }` for errors. Never mix `success: true` and `status: 'success'`.

### common/utils/attempt-limiter.ts (PIN and OTP lockout)
```ts
import { redis } from '../../config/redis';
import { TooManyRequestsError } from '../errors/app-error';

export const assertNotLocked = async (key: string, max = 5) => {
  const count = Number(await redis.get(key)) || 0;
  if (count >= max) throw new TooManyRequestsError('Too many attempts. Try again later.', 'LOCKED');
};
export const recordFailure = async (key: string, windowSec = 900) => {
  const n = await redis.incr(key);
  if (n === 1) await redis.expire(key, windowSec);
};
export const clearFailures = (key: string) => redis.del(key);
```

### common/middleware/idempotency.ts (for money-moving POSTs)
```ts
import type { RequestHandler } from 'express';
import { BadRequestError } from '../errors/app-error';

export const requireIdempotencyKey: RequestHandler = (req, _res, next) => {
  const key = req.get('Idempotency-Key');
  if (!key || key.length < 16 || key.length > 80) return next(new BadRequestError('Idempotency-Key header is required'));
  (req as any).idempotencyKey = key;
  next();
};
```
The service inserts `(user_id, idempotency_key)` with a unique constraint inside the same DB transaction as the debit. If the insert conflicts, return the existing withdrawal instead of creating another.

### common/middleware/request-id.ts
```ts
import { randomUUID } from 'node:crypto';
import type { RequestHandler } from 'express';

export const requestId: RequestHandler = (req, res, next) => {
  req.id = req.get('x-request-id') ?? randomUUID();
  res.setHeader('x-request-id', req.id);
  next();
};
```

### app.ts order
`requestId` -> `helmet()` -> `cors({ origin: allow-list })` -> `express.json({ limit: '100kb' })` -> `globalLimiter` -> request logger -> public routes (`/health`, `/auth/*` with `authLimiter`) -> `authenticate` -> feature routers -> 404 handler -> `errorHandler`. Set `app.set('trust proxy', 1)` behind a proxy.

### server.ts / worker.ts
`server.ts` only listens and handles SIGTERM/SIGINT by closing the HTTP server, then Redis and DB. `worker.ts` starts the BullMQ workers and closes them on shutdown. Also handle `unhandledRejection` and `uncaughtException` by logging and exiting so the process manager restarts it.

## 4. Conventions

- TypeScript strict (`noUncheckedIndexedAccess` on). No `any` in business code; type `req.user` once in `express.d.ts`, and type DB transactions with Drizzle's `PgTransaction` type instead of `any`.
- Controllers are thin: `asyncHandler` -> read `req.valid` -> call service -> send response. Services throw `AppError`. Repositories return plain rows.
- Wrap multi-step writes in one `db.transaction`. Side effects (queue, email, audit that must not fail the request) go through an outbox table or run after commit with their own error handling.
- Use named exports, `async/await`, early returns, and small functions. Comments explain *why*, not *what*.
- Logging: structured JSON logger to stdout, a request id on every log line, and a redaction list (`password`, `pin`, `token`, `authorization`, `privateKey`, `mnemonic`, `apiKey`).
- Git commits: offer both a detailed multi-line message and a short single-line one.
- Tests: unit-test money utils, state machines (withdrawal, sweep) and idempotency; integration-test auth, ledger concurrency (two parallel withdrawals must not overdraw) and deposit dedupe. Mock providers at the provider boundary.

## 5. How to use this skill

When reviewing: walk the checklist in section 2 and report each item as fixed, missing or not applicable, with the file and line. When building or fixing: change only what the finding requires, create any missing utility from section 3 first, explain in two or three plain sentences why the change is needed, then provide the complete file. Prioritise: critical items, then high, then database, then cleanup.
